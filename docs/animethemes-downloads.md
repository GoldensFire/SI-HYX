# AnimeThemes: отказы и проверка загрузки

Проверено 4 октября 2026 года с компьютера пользователя, без настроенного
HTTP-прокси. Использовались настоящий `v.animethemes.moe`, `requests` и
поставляемые с SI-HYX FFmpeg/ffprobe от 2026-09-02, libavformat 63.6.100.
Это наблюдения одного подключения в конкретное время, а не конфигурация сервера.

## Причина исходного провала

В журнале проблемной генерации были 14 отказов HTTP 5XX и четыре сообщения
об обрыве потока. В готовом «Тестовый № 13.siq» оказалось 24 аудиовопроса,
12 опенингов и 12 эндингов, и ни одного видео. Причины остальных шести замен
старый журнал не раскрывал. Теперь отсутствие ссылки также явно сообщается.

503 воспроизведён отдельными запросами вне программы. Сервер возвращал ответ
nginx/1.18.0; после пауз тот же адрес снова отдавал 200/206. Значит, отказ HTTP
происходит на стороне сервиса. Точная причина отказа и его внутренние лимиты
из ответов неизвестны. Таймаут подключения — отдельный сетевой сбой,
который сам по себе не доказывает отказ HTTP-сервера.

Прежний клиент усиливал нестабильность. Даже односекундное чтение FFmpeg могло
открыть четыре диапазона `bytes=0-`, `33084359-`, `155955-`, `685-`:
каждый запрос просил данные до конца файла. Замок одного генератора
ограничивал число процессов, но не запросы внутри процесса. Повтор с другого
места не устранял эту причину. Кроме того, код выхода 0 встречался вместе с
`File ended prematurely`; размера файла было недостаточно для проверки успеха.

## Где проходит граница допуска

Каждый запрос ниже читал 1024 байта целиком; серии прекращались при первом
503/таймауте. Между сериями выдерживалось восемь секунд. Время самой передачи
добавлялось к указанной паузе; это не точная частота запросов в секунду.

| Пауза после ответа | Соединение | Результат серии |
|---|---|---|
| 0 с | keep-alive | 6 ответов 206, затем 503 |
| 0 с | закрытие | таймаут первого запроса |
| 0,5 с | закрытие | 8/8 ответов 206 |
| 1 с | закрытие | 3 ответа 206, затем 503 |
| 2 с | закрытие | 4 ответа 206, затем 503 |
| 3 с | закрытие | 8/8 ответов 206 |

Один оставленный открытым полный поток не помешал контрольному запросу.
При двух потоках контрольный запрос получил 503, при трёх — 206.
После закрытия потоков и восьмисекундной паузы три контрольных запроса
прошли. **Постоянный порог «не больше двух соединений» не подтверждён.**
Так же не подтверждён постоянный порог частоты: серия с паузой 0,5 с прошла,
а с паузой 2 с — нет. Три секунды выбраны как осторожный рабочий интервал;
это не гарантия сервера. Требуются восстановление и увеличение паузы после отказа.

## Сравнение способов чтения

Для MigiToDali, начала 20 с и отрывка 15 с, сравнивалась передача с копированием
потоков без затрат на кодирование. Разброс скорости не позволяет считать
три последовательных замера гарантированным ускорением.

| Запросы FFmpeg | Время | Результат |
|---|---:|---|
| По умолчанию, без конечного байта | 58,6 с | получен отрывок |
| Блок 1 МиБ, заголовок 64 КиБ | 92,9 с | получен отрывок |
| Блок 4 МиБ, заголовок 64 КиБ | 30,8 с | получен отрывок |

Повторная серия с блоком 4 МиБ дала четыре успешные передачи: MigiToDali
55,3 с, BreakBlade1 45,2 с, MigiToDali 20,1 с, Ingress 101,0 с.
В BreakBlade1 и Ingress случился HTTP 503, после которого FFmpeg восстановился.
Простое копирование потоков давало длительности 16–35 с из-за временных
меток/ключевых кадров. В приложение перенесены параметры сетевого чтения;
конечные отрывки перекодируются и проверяются по длительности обеих дорожек.

Дополнительная проба последовательного FFmpeg-чтения через один GET не дошла
до HTTP-ответа: подключение завершилось сетевым таймаутом. На основании этой
одной пробы нельзя оценить сам способ передачи.

Шесть полных последовательных GET прошли без повторов, размер каждого
совпал с Content-Length, местный ffprobe прочитал длительность:

## Итоговая реализация

- Общая очередь сетевых этапов всех генераторов в одном процессе. Пауза
  после этапа — минимум 3 с. Запросы внутри FFmpeg управляются его HTTP-протоколом.
- Первый запрос ограничен 64 КиБ, дальнейшие — 4 МиБ; включены keep-alive,
  восстановление соединения при сетевой ошибке, 429/5XX и Retry-After.
  Повторы ограничены четырьмя, ожидание восстановления — бюджетом 30 с.
- Если FFmpeg не поддерживает эти параметры или отрывок не получен,
  скачивается целый исходник через отдельную сессию без скрытых API-повторов.
  После 408/429/5XX, обрыва или таймаута паузы составляют 8, 16, 32, 60 с;
  Retry-After может увеличить их. Всего пять попыток.
- 403/404/410 не повторяются при полном скачивании. Передача проверяется
  по размеру и сигнатуре WebM; частичные файлы удаляются. Исходник временный,
  хранится только в рабочей папке генератора и удаляется после обработки.
- Проверяются видео, звук, длительности обеих дорожек и полное декодирование
  готового файла. Нулевой код FFmpeg при незавершённом потоке не означает успех.
- По остановке прерываются ожидания и процессы; сетевое чтение имеет таймаут
  10 с на подключение/чтение. Исчерпанный резерв явно заменяется аудио песни.

## Копия отрезка вместо AV1 из сети (7 октября 2026)

Кодирование AV1 прямо из сети держало общий шлюз AnimeThemes и слот AV1 на всё
время кодирования: в прогоне 18:03 ролики шли строго по одному, «ролики —
кодирование с чтением из сети» заняло 6 мин 40 с. Медленное чтение FFmpeg ещё
и обрывалось сервером (`File ended prematurely`).

Теперь под шлюзом идёт только копия отрезка без перекодирования
(`-ss start -t (длина+2) -i URL -c copy -copyts -start_at_zero`), а AV1
кодирует её с диска с `-seek_timestamp 1 -ss start` — тот же приём, что у
отрывков серий. Копия длиннее отрезка из-за ключевых кадров, но точная резка
берёт ровно нужное: на SpyXFamily-OP1 (старт 40 с, 15 с) кадры (framemd5) и
звук (md5 PCM) совпали с резкой полностью скачанного исходника. Копия 4,7 МБ
вместо 44,7 МБ целого файла, 9–16 с; AV1 с диска (preset 10) — 3,8 с.
С 8 октября длина копии проверяется ffprobe по пакетам ещё до AV1
(`copy_short`): оборванная копия (в прогонах — 3 из 16 опенингов, 5–13 с
вместо 15) не кодируется впустую, а копируется заново — до `COPY_ATTEMPTS`
(3) раз. Исходник целиком (~1,5 мин ролика) качается, только если оборвались
все попытки или FFmpeg не умеет ограниченные HTTP-запросы.

**9 октября 2026: копия — с начала файла.** С `-seekable 0` (см. замер ниже)
FFmpeg не перематывает поток, и `-ss` до `-i` заставлял демультиплексор WebM
«пересинхронизироваться» вперёд (`Unknown element A3 … invalid data`): копия
начиналась на 2–10 с позже start, а `copy_short` мерил только конец. Отсюда
«ролик оборвался: 12.52 с вместо 15.00 с» — 19, 10 и 6 раз за прогоны 9 октября,
12 полных скачиваний, до 15 мин очереди AnimeThemes. На локальном http.server
с теми же флагами — 0 целых из 3. Теперь копия `-i URL -t (start+длина+2)
-c copy` идёт с нуля одним GET (байтов столько же: без перемотки начало и так
читалось), а `copy_short` считает кусок от `max(start, начало копии)` — 5 из 5
ровно по 15 с.


## Замер 8 октября 2026: одно соединение, один GET

С компьютера пользователя (IP вне СНГ), случайные ролики 720p/1080p из API,
отрезок 17 с с 40–50-й секунды, `-c copy`.

Одновременные копии разных файлов (пауза 20 с между сериями):

| Одновременно | Успешных | Что ломалось |
|---|---:|---|
| 1 | 1/1 (15 с) | — |
| 2 | 1/2 | `File ended prematurely` |
| 3 | 2/3 | `I/O error` при чтении |
| 4 | 1/4 | 5XX при открытии, обрывы |
| 6 | 1/6 | 5XX при открытии, обрывы |

С этого IP сервер держит одно соединение: общая очередь по одному верна.

Последовательные копии с паузой 3 с, 8 файлов на вариант:

| Чтение | Медиана копии | 503 внутри копии |
|---|---:|---|
| блоки 4 МиБ, заголовок 64 КиБ (прежнее) | 48 с (20–72 с) | 3–6 на каждую |
| блоки 32 МиБ, заголовок 1 МиБ | 25 с (12–93 с) | на половине копий |
| `-seekable 0`, один GET с начала файла | 9,5 с (8–42 с) | ни одного |

Внутри одной копии ffmpeg делал 6–10 запросов подряд, и сервер отвечал на
них 503 (переподключения ffmpeg видны только при `-loglevel warning`).
Приложение теперь читает ролик одним GET. `tools/animethemes_pack_probe.py`
на этих параметрах: 6/6 роликов по 15,015 с, декодирование без ошибок.

Генерация 40 песен (средняя 4), ещё на прежних параметрах: 31 мин, из них
29,5 мин — ожидание общей очереди; песни, ждущие очередь, занимали места
рабочих задач. Теперь на время очереди и передачи песня место отдаёт.

## Проверка через генератор и настоящий SIQ

На вход медиаэтапа поданы шесть известных ссылок, без запросов поиска аниме
и картинок. Использованы `_fetch_media`, обычное кодирование AV1 720p/Opus
192 кбит, случайная точка старта, четыре рабочих потока и `write_package`.
**Все 6/6 роликов получены; в архиве шесть видеовопросов, шесть Video-файлов,
ноль Audio-файлов.** Длительность контейнеров 15,015 с, видео 14,973–15,015 с,
звук 15,000 с. Каждый ролик полностью декодирован без ошибок.

Отдельный прогон с принудительно отключённым быстрым путём получил целый
MigiToDali, вырезал и проверил отрывок, собрал SIQ с одним видеовопросом
и без аудиозамены; весь прогон занял 12,0 с. Скорость сервиса заметно меняется.
Это подтверждает резервную ветку, но не гарантирует отсутствие будущих 503.

Проверочные пакеты и исходные результаты расположены в
`artifacts/animethemes-validation/`. Автотесты проверяют закрытие ответов,
общие паузы, Retry-After, отмену, обрывы, постоянные ошибки, совместимость
FFmpeg и недопустимость повреждённых/укороченных дорожек.

Проверки генератора и интерфейса: **1622 passed**. Финальный целевой прогон
загрузчика, видео, галочки песен и подписи Chiptune: **55 passed**.
Проверка гигиены и размеров прошла. В полном наборе pytest остался один
ранее воспроизводившийся сбой вне загрузчика:
`test_custom_tooltip_regions.py::test_leaving_custom_cell_never_retains_its_text[row]`
(подсказка прячется при переходе между строками вместо показа новой).

Для повторения (это реальные сетевые загрузки):

```powershell
python tools/animethemes_probe.py boundary
python tools/animethemes_probe.py full
python tools/animethemes_stream_probe.py
python tools/animethemes_stream_probe.py --size 4194304 --count 3
python tools/animethemes_pack_probe.py
python tools/animethemes_pack_probe.py --count 1 --offset 1 --parallel 1 --force-full
```

Параметры протокола описаны в [официальной документации FFmpeg](https://ffmpeg.org/ffmpeg-protocols.html#http).
NGINX действительно может выдавать 503 при
[ограничении запросов](https://nginx.org/en/docs/http/ngx_http_limit_req_module.html)
или [соединений](https://nginx.org/en/docs/http/ngx_http_limit_conn_module.html),
но это не подтверждает, какие именно модули/лимиты использует AnimeThemes.
