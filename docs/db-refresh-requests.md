# Выдача тайтлов при обновлении базы

Проверено живыми запросами **2026-10-01**. Изменения относятся к обновлению
каталогов, расчёту популярности и сбору частей франшиз.

| Источник / раздел | Раньше за HTTP-запрос | Теперь | Ограничение |
| --- | ---: | ---: | --- |
| Shikimori: полные карточки аниме | 50 | 100 | 2 страницы × 50; сложность 134 |
| Shikimori: полные карточки манги | 50 | 200 | 4 страницы × 50; сложность 188 |
| Shikimori: книжная популярность | 50 | 750 | 15 страниц × 50; сложность 180 |
| Shikimori: части франшиз | до 156 | до 650 | 13 франшиз × 50 частей; сложность 182 |
| ReManga: каталог с закладками | 30 без закладок | 40 с закладками | `/api/titles/`, фактический максимум 40 |
| MangaLib: каталог | 60 по умолчанию | 60 явно | серверный максимум `limit=60` |

Shikimori ограничивает одну страницу 50 тайтлами и весь GraphQL-документ
190 единицами сложности. Последовательные страницы объединены алиасами с
сохранением всех прежних полей полных карточек, фильтров и сортировки `order=id`.
Полная страница аниме стоит 67 единиц, манги — 47; соответственно третья и
пятая страницы уже не помещаются. Это подтверждено ответами сервера: 6 страниц
аниме отклонены со сложностью 402, 5 страниц манги — со сложностью 235.

Для независимого книжного census нужны только `id`, `kind`, `score`, `status`,
`airedOn.year`, `releasedOn.year`, `statusesStats`. Эти поля сохраняют прежний
расчёт `own_base` и `book_index`, включая закэшированное избранное. Облегчённая
выборка стоит 12 единиц на страницу и позволяет собрать 750 тайтлов за запрос.
Фильтры конкретного пака в census не попадают.

Основания пределов Shikimori: [схема GraphQL](https://github.com/shikimori/shikimori/blob/master/app/graphql/shikimori_schema.rb),
[выборка аниме](https://github.com/shikimori/shikimori/blob/master/app/graphql/queries/animes_query.rb),
[выборка манги](https://github.com/shikimori/shikimori/blob/master/app/graphql/queries/mangas_query.rb).

Поисковый каталог ReManga на `count=100` возвращает HTTP 400 с `max_value=30`,
включая `/api/v2/search/catalog/`, и не содержит `count_bookmarks`. Вместо него
используется `/api/titles/`: выдаёт 40 записей с закладками, лицензией, типом,
названиями и годом. При `count=100/1000` выдача ограничивается 40; проверены
страницы 1/2, 469, 1359/1360 и пустые страницы за концом каталога.
MangaLib на `limit=100` и `limit=120` возвращает
HTTP 422: допустимый диапазон — 10–60. `per_page`, `count`, `page_size`
не увеличивают выдачу MangaLib: сервер всё равно сообщает `meta.per_page=60`.
Поэтому используются подтверждённые максимумы действующих публичных API:
[ReManga](https://xn--80aaig9ahr.xn--c1avg/api/titles/?page=1&count=40&ordering=id&content=manga),
[MangaLib](https://api.cdnlibs.org/api/manga?site_id%5B%5D=1&page=1&limit=60&sort_by=created_at&sort_type=asc).

Границы страниц сохраняются: конец каталога определяется по пустой странице,
потолок страниц не превышается, отсутствующий/некорректный алиас считается
ошибкой. При остановке уже полученные карточки сохраняются; следующий запрос
не отправляется. При снижении серверного бюджета клиент уменьшает пачку,
повторяет её с той же начальной страницы и запоминает размер до конца сессии.
Отдельные страницы избранного и детали MangaLib имеют контракт «один тайтл за
запрос». ReManga добирает детали только при неполной карточке пакетного каталога.
При полном обновлении ReManga и MangaLib собираются одновременно с Shikimori;
общая запись файла базы сериализуется, частичные данные сохраняются при stop.

Реализация: `si_hyx_parts/animepack_api/shikimori_catalog.py`, общий обход —
`si_hyx_parts/animepack/catalog_pages.py`. Регрессионные проверки —
`tests/test_animepack_catalog_requests.py`.
