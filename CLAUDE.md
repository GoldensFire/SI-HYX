# Правила разработки SI-HYX

## Структура кода

- Карта проекта — [CODE_MAP.md](CODE_MAP.md): какие модули за что отвечают и где
  искать нужное поведение. Сначала найди символ через `rg -n`, затем читай файл.
- Публичные модули в корне (`main.py`, `edit_tab.py`, `animepack.py`, `config.py`
  и другие) — точки входа и API для приложения, тестов и `tools/`. Небольшой
  компонент живёт целиком в своём публичном модуле. Реализация крупного лежит в
  `si_hyx_parts/<имя модуля>/`, а публичный модуль её реэкспортирует.
- Один модуль — один связный компонент или тема. Объединяй тесно связанный код,
  не объединяй независимые компоненты. Имя файла называет содержимое
  (`playback.py`, `settings_store.py`), а не первую функцию в нём.
- Длина файла — не цель и не запрет. Файлы длиннее 1500 строк CI отмечает
  предупреждением (`python tools/check_file_sizes.py`): это повод проверить, не
  пора ли выделить самостоятельную часть. Не дроби связный код ради числа строк.
- Не используй `exec`, `eval` и подгрузку исходников во время выполнения:
  сборщик и pyflakes должны видеть обычные статические импорты.
- Сам CLAUDE.md держи коротким; подробности размещай рядом с кодом или в CODE_MAP.md.

## Классы

- Методы пишутся в теле класса. Не импортируй функции в тело класса как методы.
- Крупный класс собирается из миксинов по ответственности: `EditTab` наследует
  `EditTabLayoutMixin`, `EditTabPlaybackMixin`, `EditTabExportMixin` и другие.
  Миксин лежит рядом с классом, не определяет `__init__` и сигналы Qt; они
  остаются в основном классе. Состав крупных классов — в CODE_MAP.md.
- В методах используй обычный `super()`. Имена методов в миксинах одного класса
  не должны повторяться.
- Логику, которой не нужно состояние объекта, оформляй функциями с явными
  параметрами в тематическом модуле.

## Совместимость

- Модули в `si_hyx_parts/` обращаются к публичному модулю через `_api`
  (`import edit_tab as _api`). Так все части видят общие настройки, кеши, пути
  ресурсов и подменённые в тестах зависимости. Не копируй изменяемое состояние
  в модули частей.
- Публичный модуль загружает части в определённом порядке; при импорте часть
  может использовать только уже определённые в нём имена.
- Сохраняй публичные имена: приложение, тесты и инструменты импортируют их из
  публичных модулей.

## Проверки по задаче

- Не создавать и не дописывать автотесты без явного запроса пользователя.
- Не запускать полный набор тестов без явного запроса пользователя.
- Проверять результат соразмерно изменению: просмотром правки, проверкой
  синтаксиса или конкретного изменённого сценария. Точечные существующие тесты
  запускать только при конкретной необходимости, без повторных прогонов
  при отсутствии новых изменений или ошибок.
- Проверка гигиены (`python tools/check_hygiene.py`: pyflakes, явная кодировка,
  голые `except`, правила CodeQL) и полный набор тестов выполняются в CI. Локально гигиену
  запускай при изменениях, затрагивающих её правила.

## Безопасность (CodeQL)

- Хост URL проверяй только разбором: `urlsplit(url).hostname == "x.com"` или
  `host_matches()` из `config`. Не `"x.com" in url`, не
  `url.startswith("https://x.com")` без «/», не `endswith("x.com")` без точки —
  в тестах тоже.
- В регулярках под `*`/`+` ветки не должны пересекаться (`(?:\\.|[^\\])*`, а не
  `(?:\\.|.)*`), без вложенных повторов вида `(\w+\s?)*`.
- Пути из сети и `.siq` не склеивай с папками без проверки (zip-slip), XML
  разбирай без внешних сущностей, данные запроса не отправляй в заголовки/URL
  без проверки.
- Перед концом сессии с правками кода: `python tools/check_security.py`
  (быстро, без тестов). Открытые алерты GitHub: `python tools/check_security.py --alerts`.
